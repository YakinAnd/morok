# morok MCP server — design spec

Date: 2026-07-26
Status: Approved (design phase) — implementation plan pending

## Problem

Every morok `enum --report` run produces a self-contained HTML report with rich findings (ACL, ADCS, Kerberos, vuln-checks, attack paths, etc.), each carrying exploit commands and remediation guidance as rendered text. There is no way for an LLM agent (or any external tool) to query that data programmatically — a red teamer wants "what should I attack next and how," a blue teamer wants "what should I fix first and how," and today both have to read the HTML by eye.

Separately, while reviewing this design we found that the report's embedded `morok-data` JSON snapshot (`internal/report/html.go:buildSnapshot`) — the same blob the History tab uses to diff two reports — has no entry for vulnerability-check findings (`--vuln-check` / `analysis.VulnResult`) at all. A DC patched for Zerologon between two scans currently shows no change on the History tab. This is fixed as part of the same schema work below, since both problems point at the same root cause: the snapshot schema is a lossy fingerprint, not a full structured export.

## Goals

- Give an MCP client (Claude Code, Claude Desktop, or any MCP-compatible agent) structured, queryable access to a single morok HTML report's findings.
- Provide separate **redteam** and **blueteam** tool namespaces reflecting how each audience would use the same data differently.
- Fix the History tab gap: vulnerability-check findings become part of the diffable `Findings` map.
- Keep the report a single self-contained HTML file — no separate export step required to use the MCP server; it reads what `enum --report` already produces.

## Non-goals (this iteration)

- Live/on-demand scanning through the MCP server (no wrapping of `morok enum` itself). Input is always an already-generated report.
- Multi-report sessions (comparison, multi-domain merge across reports) via MCP — out of scope; the MCP server operates on exactly one report per process lifetime.
- Built-in ML/heuristic ranking beyond what morok's existing BFS attack-path computation and severity/CVSS fields already provide.
- Non-Go implementation. No Python/TS MCP server.

## Architecture

```
enum --report r.html            morok mcp --report r.html
       │                                  │
       ▼                                  ▼
internal/report                  internal/mcpserver
  buildSnapshot() v2  ──writes──►  parser.go  ──reads──►  server.go (MCP tools)
  <script id="morok-data">        (extract + unmarshal)    (stdio transport)
```

- **`internal/report`** (existing package) gains a versioned snapshot schema. `buildSnapshot` now emits `v: 2` with the richer structure described below. Parsing of `v: 1` snapshots (old reports, used by the History tab today) continues to work unchanged — this is purely additive.
- **`internal/mcpserver`** (new package):
  - `parser.go` — given a path to a morok `.html` report, extracts the `<script id="morok-data">…</script>` block and unmarshals it into the v2 Go structs. Rejects `v: 1` reports with a clear error ("regenerate this report with a morok version that supports vuln-check data").
  - `server.go` — wires up an MCP server (stdio transport, likely `github.com/mark3labs/mcp-go`) and registers the tool set described below.
- **`cmd/morok`** gains a new subcommand: `morok mcp --report <path.html>`. The report path is required at process start; there is no `load_report` tool in this iteration (single-report-per-session, per the approved design).

## Data model — snapshot v2

The existing `snapshot` struct in `buildSnapshot` (`internal/report/html.go`) changes from `Findings map[string][]string` (fingerprint strings like `"principal|right|target"`) to structured entries per category. Each category's finding gains, where applicable: `Severity`, `CVSS`, `Detail`, `Remediation`, `ExploitCommand`.

New category: **`vulns`**, built directly from `VulnResult.Findings` (`internal/analysis/vulns.go`) — one entry per finding with `CVE`, `Name`, `Status` (candidate/confirmed/unreachable), `Host`/`FQDN`, `Detail`, `Remediation`. This is what closes the History tab gap: these entries flow through the same Regressions/Resolved/Outstanding diff logic every other category already gets. Risk Score itself is unchanged — vuln findings still do not contribute to the computed score, matching the existing ADP-194 decision.

Attack paths (`d.AttackPaths`) gain their edge list in the snapshot (today only a flattened string like `"jsnow→Domain Admins(2hops)"`); the MCP server needs the edges to reconstruct the path for the redteam tool.

Version gate: `v: 1` reports (generated by older morok binaries) are readable by the History tab exactly as today. They are **not** readable by `morok mcp` — there is nothing to serve for exploit commands / vuln detail that isn't in the v1 blob, so the MCP server errors out with a message telling the user to regenerate the report.

## Tool surface

**Redteam**
- `list_attack_paths` — all BFS paths, sorted by depth, with target group.
- `get_attack_path(target_group)` — full node/edge detail for paths ending at a specific privileged group.
- `list_confirmed_vulnerabilities` — vuln findings with `Status == confirmed` (from `--vuln-check` active probes).
- `get_exploit_commands(finding_ref)` — the exploit command text for a specific finding, by reference (category + index or a stable id — exact addressing scheme is an implementation-plan detail).

**Blueteam**
- `list_findings(severity?)` — all findings, optionally filtered by severity.
- `get_remediation_checklist(category?)` — remediation text grouped by category (ACL, ADCS, vuln-checks, etc.), optionally filtered to one category.
- `get_vulnerability_summary` — counts of candidate/confirmed/unreachable vuln findings, mirroring the CLI's `[VULNS]` section.

**Shared**
- `get_report_summary` — domain, generated_at, version, grade, score, critical/high/medium counts.
- `list_categories` — which finding categories have data in this report (so a client doesn't have to guess).

## Error handling

- Report path missing or unreadable at startup → process exits with a clear, non-zero error (matching morok's existing friendly-error conventions in `internal/ldap/errors.go`).
- `morok-data` script tag missing or its JSON fails to parse → surfaced as a tool-call error to the MCP client, not a crash.
- `v: 1` report loaded → explicit "this report predates vuln-check/MCP data — regenerate with a current morok version" error at startup.

## Testing

- Unit tests for `buildSnapshot` v2 in `internal/report` — verify vuln findings appear in the snapshot's `Findings["vulns"]`, verify severity/CVSS/remediation fields are populated, verify v1 output remains parseable by the existing History-tab-facing code path.
- Unit tests for `internal/mcpserver/parser.go` against small fixture HTML files (hand-built, embedding both a v1-style and a v2-style `morok-data` block) — verify correct extraction, correct version-gate rejection of v1.
- Manual smoke test: run `morok mcp --report demo-after.html` (existing `cmd/gendemo2` output, already has vuln findings) against a real MCP client and exercise each tool at least once.

## Open questions for the implementation plan

- Exact addressing scheme for `get_exploit_commands(finding_ref)` — stable finding IDs vs. category+index.
- Which Go MCP SDK to depend on (`mark3labs/mcp-go` assumed here, not yet verified against current maintenance status/API surface).
- Whether `internal/mcpserver` needs its own `go.mod` (separate module) or stays in the main morok module — affects build tooling and dependency footprint of the core CLI.
